## 1. 模倣元「Setlog」の仕組み分解

| # | Setlogの仕様 | 本アプリでの扱い |
|---|---|---|
| 1 | 1時間ごとに通知が来て、**2秒の動画**を撮る | **踏襲**。通知起点の手動撮影（自動撮影はOS制約で不可） |
| 2 | インカメ／アウトカメどちらでも可。**無音** | **踏襲**。動画録画のため原則無音 |
| 3 | **加工不可。カメラロールの動画も使えない** | **踏襲**。これが「その時間に働いていた」証跡になる |
| 4 | 動画と一緒に**短いテキスト**を添えられる | **踏襲**＋業務用の「作業タグ」を追加 |
| 5 | 「ログ」＝グループに2〜12人が招待コードで参加 | **改変**。部署への所属＝ログへの参加。管理者が管理 |
| 6 | **人数に応じて分割数が変わる分割画面**で1本に合成 | **拡張**。人数上限を撤廃（4.3節） |
| 7 | 1日分が自動結合され、書き出しでVlogが完成 | **踏襲**＋深夜バッチで自動生成 |
| 8 | 1人だけで記録する**ソロログ**もある | **踏襲**。個人ログ＝日報・勤怠の元データ |
| 9 | 認証を省いた軽いオンボーディング | **改変**。クライアント企業のGoogle Workspaceアカウントでログイン |

### 1.1 Setlogをそのまま業務に使うと詰まるところ

| 詰まる点 | 内容 |
|---|---|
| 組織構造がない | 30部署を束ねる概念がなく、ログが乱立する |
| 横断して見られない | 部長・役員が複数部署を見る手段がない |
| 撮影の有無を管理できない | 「誰が撮っていないか」を集計できない |
| 日報にならない | 動画は残るが、結局テキストの日報を別途書くことになる |
| 勤怠に使えない | 分単位の時刻を取り出せず、エクスポート手段がない |
| データが会社の管理下にない | 退職者、保存期間、監査ログ、削除要求に対応できない |

> **追い風**：Setlogが2026年春に若年層で大流行したことで、「1時間ごとに2秒動画を撮る」という行動様式が社会に受け入れられました。
> 新しい操作を覚えさせる提案ではなく、**「知っているあれの、業務版」**として提案できるのは導入障壁の面で大きな利点です。

## 2. スコープ

### 2.1 MVP（フェーズ0〜2）
- Google Workspace SSOによるログインと、マルチテナントのデータ分離
- 通知起点の2秒動画撮影（分単位タイムスタンプ・加工不可）
- ログ（部署／個人）と、スクロール可能なサムネイルグリッド
- 日次Vlogの自動生成
- AI日報案の自動生成 → 本人が編集して提出
- 本人によるデータ削除

### 2.2 フェーズ3〜5
- 組織階層・権限・テナント管理Web
- 勤怠集計・CSVエクスポート・修正申請
- ストア公開、パイロット運用

### 2.3 フェーズ6以降
- Google Workspaceからのユーザー／組織部門の自動同期
- 既存勤怠システムとのAPI連携
- 全社ダッシュボード、週報・月報の自動生成
- リアクション／コメント

### 2.4 スコープ外
給与計算／経費精算／チャット／位置情報の取得

## 4. 機能要件

### 4.1 撮影

| ID | 要件 |
|---|---|
| F-101 | 稼働時間中、**1時間ごとにプッシュ通知**を配信する |
| F-102 | 通知タップ → カメラ起動 → **2秒動画**を撮影（自動で2秒停止） |
| F-103 | **インカメ／アウトカメ**を切替可。ログごとに初期値を設定できる |
| F-104 | **無音撮影**。動画録画のためiOSでは原則無音。Android主要機種での実機確認を受け入れ条件に含める |
| F-105 | **撮影時刻は秒精度で保存し、分単位で表示**する（例：`12:04`）。DB・UIとも丸め処理を入れない |
| F-106 | **加工不可。カメラロールからの選択も不可**。その場で撮影したものだけを受け付ける |
| F-107 | **一言メモ**（任意・100字程度）を入力できる |
| F-108 | **作業タグ**（営業／開発／会議／移動／事務 等・テナントごとに定義）を選択できる |
| F-109 | 撮影猶予時間を設定できる（既定：通知から50分）。超過は「未撮影」扱い |
| F-110 | 猶予後の後追い撮影は可能だが「**遅延**」フラグを付ける |
| F-111 | 撮影間隔（30分／1時間／2時間）と稼働時間帯を**テナント／部署ごとに設定**できる |
| F-112 | オフライン時はローカル保存し、通信回復時に自動アップロード。アプリ復帰時にも再開処理を行う |
| F-113 | 「撮影しない時間」（休憩・私用外出）を申告でき、通知を止められる |
| F-114 | 通知に反応がない場合、**15分後に1回だけ再送**する |
| F-115 | 動画仕様を固定する：**720p / H.264 / 約2Mbps / 2秒**（1本あたり約0.5〜2MB） |
| F-116 | 通知の配信時刻に**0〜3分のばらつき**を持たせ、アップロードの集中を平準化する |

### 4.2 ログ

| ID | 要件 |
|---|---|
| F-201 | **部署ログ**：部署に所属するメンバーの撮影が自動的に集まる（所属＝参加、招待コード不要） |
| F-202 | **個人ログ**：全メンバーが自動で1つ持つ。日報・勤怠の元データ |
| F-203 | **1ログあたりの人数上限を設けない**。表示側で吸収する（4.3節） |
| F-204 | 1ユーザーが**複数のログに所属**できる（兼任） |
| F-205 | 期間限定の**プロジェクトログ**（部署横断・招待制）※フェーズ6 |

> 用語は「ログ」に統一する（グループ／ルーム／チームとは呼ばない）。

### 4.3 閲覧とVlog生成

**レビューを受けて、「動くグリッド」と「動画」を分離した。**
v0.3では複数の動画をアプリ内で同期再生する想定だったが、端末の同時デコード数の制約が大きく、実装・検証コストに見合わない。
**「大人数を見る」はサムネイルグリッドで、「動画で見る」はサーバー生成の1本で**という切り分けにする。

| 層 | 実体 | 人数 | スクロール |
|---|---|---|---|
| **A. サムネイルグリッド** | 各コマの静止画サムネイルをタイル表示（アプリ内） | **上限なし** | **可能** |
| **B. 書き出しVlog** | FFmpegで合成した1本のmp4 | 1画面Nコマ、超過分はページ送り | 動画なので不可 |

| ID | 要件 |
|---|---|
| F-301 | **【A】サムネイルグリッド**：ログのメンバー×時間帯をタイル状に表示する。**縦スクロールで何人でも閲覧でき、人数上限はない**。動画を同時再生しないため端末負荷はほぼゼロ |
| F-302 | 【A】1画面あたりの分割数を**4／6／9／12**から選択できる（既定は実機検証で決定） |
| F-303 | 【A】タイルをタップすると、その2秒動画を**単体で再生**する |
| F-304 | 【A】未撮影は**空きコマ**、本人が削除したものは**削除済み枠**として表示する |
| F-305 | 【A】並び順を選べる（氏名順／撮影時刻順／未撮影を先頭） |
| F-306 | **【B】書き出しVlog**：1日の撮影分を時系列に結合し、深夜バッチで1本生成する |
| F-307 | 【B】1画面Nコマで合成し、**N人を超える分はページ送り**で表示する（例：30人・12分割なら3ページを順に再生） |
| F-308 | 【B】ページ単位に分割した複数本としても書き出せる |
| F-309 | 【B】各カットに**撮影時刻（分単位）と氏名**を焼き込む |
| F-310 | ユーザーがその場で**手動書き出し**もできる（Setlogの「書き出し」相当） |
| F-311 | 生成完了時にプッシュ通知。再生・ダウンロード・共有リンク発行が可能 |
| F-312 | 共有リンクは**ログイン必須かつ同一テナント内限定**を既定とする。認証なしリンクを許可する場合は有効期限（最長7日）とパスワードを必須とし、発行を監査ログに残す |
| F-313 | BGMの有無、1カットの表示秒数、グリッドレイアウトを設定できる |

> **実装メモ**：【B】の合成はFFmpegの `xstack` フィルタでグリッド定義を動的生成し、ページ数分を `concat` する。

### 4.4 AI日報

| ID | 要件 |
|---|---|
| F-401 | その日の「**撮影時刻＋メモ＋作業タグ（＋フレーム画像）**」を入力に、**日報案を自動生成**する |
| F-402 | **「テキストのみモード」を用意する**。メモと作業タグだけで生成し、映像を外部APIに送らない。テナント単位で選択でき、既定はこちら |
| F-403 | 日報テンプレートは**テナント／部署ごとに設定可能**（例：本日の業務／進捗／課題／明日の予定） |
| F-404 | 生成された案は**必ず本人が確認・編集して提出**する。自動確定はしない |
| F-405 | 提出済み日報は「**Vlog＋テキスト**」の1セットで表示される |
| F-406 | 未提出者へ所定時刻にリマインド。締め時刻の既定は**翌日正午**（テナントごとに設定可） |
| F-407 | 部署管理者は自部署の日報一覧を閲覧・コメントできる |
| F-408 | 撮影やメモが少ない日は、**AIに業務内容を推測させず「情報が不足している」と明示させる** |

### 4.5 テナントと認証

**レビューを受けて方式を変更。テナント判定をアプリのコードから完全に排除する。**

| ID | 要件 |
|---|---|
| F-501 | **クライアント企業のGoogleアカウントでログイン**する（Google Workspace SSO / OIDC）。独自パスワードは持たない |
| F-502 | **初回ログイン時のみ**、サーバー側でIDトークンの`hd`クレームを検証し、登録済み許可ドメインと照合する |
| F-503 | 照合が通ったら、**Firebase Custom Claimsに`tenantId`を焼き込む**。以降のアクセス制御は`request.auth.token.tenantId`のみで判定し、**アプリのコードはテナント判定に一切関与しない** |
| F-504 | **個人のGmailアカウントではログインできない**（登録済みWorkspaceドメインのみ許可） |
| F-505 | 全データを `/tenants/{tenantId}/` 配下に置き、**テナント越境をFirestore／Storageのセキュリティルールで機械的に禁止**する |
| F-506 | テナントごとの設定：撮影間隔、稼働時間帯、休日カレンダー、タイムゾーン、作業タグ、日報テンプレート、締め時刻、グリッド分割数、AIモード、データ保持期間、ロゴ・テーマカラー |
| F-507 | Workspace側でアカウントが無効化された利用者は、**次回ログイン時にアクセス不可**となる |
| F-508 | テナント管理者を1名以上設定し、その企業内のユーザー・部署・設定を管理させる |
| F-509 | 提供者（FREX）側の運用管理画面：テナントの追加・停止、許可ドメイン登録、利用状況の確認。**テナントの業務データは既定で閲覧不可**とし、閲覧した場合は監査ログに残す |
| F-510 | GCPのリージョンを**東京（asia-northeast1）に固定**し、データが国外に出ない構成とする |

> **導入時にクライアント側で必要になるもの**：① Google Workspaceの利用 ② 利用ドメインの申告 ③（自動同期を使う場合）管理コンソールでのアプリ承認

### 4.6 組織・権限

| ID | 要件 |
|---|---|
| F-601 | 部署を**階層構造**（本部＞部＞課）で管理できる |
| F-602 | 権限は3階層：メンバー／部署管理者／テナント管理者 |
| F-603 | 部署管理者は**自部署配下のみ**閲覧可能 |
| F-604 | 個別ユーザーに横断閲覧権限を付与できる（役員・人事など） |
| F-605 | 入退社・異動に対応。**過去データは異動前の部署に紐づいたまま保持** |
| F-606 | 退職者アカウントの即時無効化と、データ保持ポリシーの適用 |

### 4.7 勤怠

| ID | 要件 |
|---|---|
| F-701 | 当日の**初回撮影＝出勤時刻候補**、**最終撮影＝退勤時刻候補**として記録する |
| F-702 | 明示的な「出勤／退勤／休憩開始／休憩終了」操作を別途持つ |
| F-703 | 撮影ログから**分単位の稼働時間・空白時間**を自動算出する |
| F-704 | 月次の勤怠CSVを社員別・部署別に出力できる |
| F-705 | 打刻の修正申請 → 部署管理者の承認フロー |
| F-706 | 本人が映像を削除した場合も、**時刻の記録は保持**する（勤怠の整合性を守るため） |

> ⚠️ **労務上の留意点**：撮影記録をそのまま法定の労働時間管理に用いる場合、就業規則への明記と労使での事前合意、および顔画像の取扱いの整理が必要です。
> **MVPでは「既存勤怠への補助エビデンス＋CSV連携」に留める**ことを推奨します。

### 4.8 管理・監査

| ID | 要件 |
|---|---|
| F-801 | ホーム：次の撮影時刻、当日の自分のコマ、日報ステータス |
| F-802 | 部署ビュー：メンバー別のサムネイルグリッド、撮影率 |
| F-803 | 全社ビュー：部署一覧と撮影率（テナント管理者のみ） |
| F-804 | 期間・部署・ユーザー・作業タグでの絞り込み検索 |
| F-805 | 誰がいつ誰のデータを閲覧・削除したかの**監査ログ**を保持する。**追記専用とし、テナント管理者からも削除できない** |
| F-806 | 解約時に、テナントの全データをエクスポートし、その後完全削除する手順を提供する |

### 4.9 本人によるデータ削除【新設】

意図しない写り込み（私物・同僚・家族・顧客・機密資料）は必ず発生する。**本人が消せない設計は、それだけで導入が止まる。**

| ID | 要件 |
|---|---|
| F-901 | 本人は自分の撮影を**いつでも削除できる**（理由の入力は任意） |
| F-902 | 削除されたコマは「**削除済み**」として枠だけ残り、映像のみ消える |
| F-903 | 削除は**5分以内に全経路**（サムネイルグリッド／Vlog／共有リンク／ダウンロード済みでない配信）から反映される |
| F-904 | 削除は監査ログに残る。**テナント管理者でも映像は復元できない** |
| F-905 | すでに生成済みのVlogは、削除発生時に**該当コマを空きコマにして再生成**する |

## 5. 運用ケース定義【新設】

レビューで最も多くの抜けが見つかった領域。ここが未定義だと、稼働初週で不信感につながる。

| ケース | 定義 |
|---|---|
| **休日・祝日** | テナントごとに休日カレンダーを設定する。設定日は**通知を配信せず**、撮影率の分母にも含めない |
| **業務日の定義** | **勤務開始時刻が属する日**を業務日とする。日付をまたぐ勤務も1つの業務日にまとまる |
| **シフト・夜勤** | 勤務区分（通常／シフト／夜勤）を持ち、稼働時間帯を区分ごとに設定する。Vlog生成と勤怠集計は業務日基準で行う |
| **有給・欠勤・直行直帰** | 勤務区分として申告でき、その日は通知を止め、**撮影率の分母から除外**する |
| **タイムゾーン** | テナント単位で設定する（既定：Asia/Tokyo）。通知・集計・Vlog生成のすべてがこれに従う |
| **中途入社・退職** | 在籍期間内のみを撮影率の分母とする |
| **異動** | 異動日以降の撮影は新部署のログへ。過去分は旧部署に残る |
| **通信不良の現場** | オフラインキューに保持し、復帰時に元の撮影時刻のまま送信する（時刻は撮影時点を保持） |

## 6. 画面一覧（MVP）

| # | 画面 | 主な要素 |
|---|---|---|
| 1 | ログイン | 「Googleでログイン」のみ。ドメインでテナント自動判定 |

## 8. システム構成

```
[モバイルアプリ]  Expo (React Native) / TypeScript
      │
      │ ① Googleでログイン
      ▼
[認証]  Firebase Auth（Googleプロバイダのみ）
      │  初回のみ hd を検証 → Custom Claims に tenantId を付与
      │
      │ ② 撮影 → 署名付きURLを取得
      ▼
[Cloud Functions]  署名付きURL発行 / API / 通知スケジューラ
      │
      │ ③ 端末から Cloud Storage へ「直接」アップロード（★スパイク対策）
      ▼
[Cloud Storage]  /tenants/{tenantId}/captures/...  ＋ CDN
      │
      │ ④ アップロード完了イベント
      ▼
[Firestore]  /tenants/{tenantId}/...
      │
      │ ⑤ 深夜バッチ
      ▼
[Cloud Run Jobs]
      ├─ FFmpeg (xstack) で分割画面Vlogを生成・時刻焼き込み
      └─ Claude API で日報案を生成（テキストのみ／画像ありを切替）
      │
[管理Web]  Next.js（テナント管理／提供者管理）
[通知]     Cloud Scheduler → FCM / APNs
```

**設計上の要点**

1. **アップロードはサーバーを経由しない。** 端末から署名付きURLでCloud Storageへ直接送る。毎正時のスパイクに対して、これが最も効く対策
2. **テナント分離はセキュリティルールで担保する。** アプリ側の実装ミスで他社のデータが見えることがない構造にする
3. **アプリ内で複数動画を同時再生しない。** サムネイルグリッド＋単体再生＋サーバー生成Vlogの3本立て
4. **集計はバッチで行う。** Firestoreの単一ドキュメント書き込み制限を避けるため、撮影率などは日次バッチか分散カウンタで集計する

### 9.4 事業モデルの結論

| モデル | 内容 | 評価 |
|---|---|---|
| A. 受託開発のみ | 1社向けに作り、納品して終わり | 回収は確実だが、資産が残らない |
| B. 自社SaaS | FREXが開発投資し、複数社に売る | 開発費1,000万の回収に**10社×1年**が必要。先行投資リスクが大きい |

**Cを推奨します。** 契約時に「著作権はFREXに帰属し、クライアントには利用権を許諾する」形にしておくことが前提条件です。ここを詰めずに着手すると、後から横展開できなくなります。

## 14. リスク

| リスク | 影響 | 対応 |
|---|---|---|
| **「監視ツール」と受け取られ現場が抵抗する** | **定着しない（最大のリスク）** | 目的を「日報を書かなくてよくする」と位置づける。アウトカメラ既定を選べるようにする。本人がいつでも削除できることを明示する |
| テナント間のデータ混在 | 致命的。事業継続に関わる | Custom Claims＋セキュリティルールで機械的に分離。分離テストを回帰項目に |
| 通知を無視され撮影率が下がる | データが欠ける | 空きコマの可視化、撮影率の表示、間隔を2時間に緩められる設定 |
| AI日報の品質が低く結局手書きになる | 主目的が未達 | メモ・作業タグの入力設計を先に固める。受け入れ基準6で品質を担保 |
| 外部APIへのデータ提供が情シス審査で止まる | 導入停止 | テキストのみモードを既定にし、説明資料を標準添付 |
| ストア審査で従業員監視アプリとして差し戻される | リリース遅延 | プライバシー説明を丁寧に用意し、審査期間をスケジュールに織り込む |
| Setlogが法人版を出す | 競合発生 | 日報AI・勤怠・組織管理という業務側の作り込みで差別化する |
| 1社目のパイロットで使われない | 事業ごと再検討 | プランAの検証版で早期に判明させる（これがプランA最大の価値） |
