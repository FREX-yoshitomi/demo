# セットアップ手順（人がやる作業）

要件定義書 付録 A.2 の一覧を、実際の手順に落としたもの。
**コードでは自動化できない部分だけ**を書いている。

対象：クライアント1社目への社内リリース（パイロット）まで。

## 0. 着手前に確定させること

要件定義書 第13章より、これが決まらないと先に進めない。

| # | 論点 | 影響 |
|---|---|---|
| 1 | 1社目のクライアント | 許可ドメイン・パイロット部署がすべてここに依存する |
| 2 | 著作権と横展開権の契約条件 | 後から変更できない。着手前に合意が必要 |

加えて、実装済みの範囲に直接効くもの：

| 項目 | 既定値 | 決め方 |
|---|---|---|
| 撮影間隔 | 60分 | パイロット部署の業務実態。2時間に緩められる (F-111) |
| 稼働時間帯 | 09:00-18:00 | 部署ごとに上書き可 |
| 撮影猶予 | 50分 | 超過分は遅延フラグ付きで受理される (F-110) |
| グリッド分割数 | 6 | **実機検証で確定させる**（要件定義書 #8） |
| 既定カメラ | アウトカメラ | 顔を映さない選択肢を用意することが定着の鍵（要件定義書 第14章） |
| AIモード | テキストのみ | 原価が半分以下になる。画像ありは情シス審査が重くなる |

## 1. Apple Developer Program（**最初に着手する**）

法人登録には D-U-N-S 番号が必要で、取得に数日〜2週間かかる。
ここが全体のクリティカルパスになりやすい。

1. D-U-N-S 番号を確認・取得（https://developer.apple.com/enroll/duns-lookup/）
2. Apple Developer Program に法人として登録（$99／年）
3. App Store Connect でアプリを登録（Bundle ID: `works.frex.worklog`）

### APNs 鍵の発行（プッシュ通知に必須）

1. Certificates, Identifiers & Profiles → Keys → 新規キー
2. **Apple Push Notifications service (APNs)** を有効にして作成
3. `.p8` ファイル（1回しかダウンロードできない）と Key ID / Team ID を保管
4. Firebase Console → プロジェクト設定 → Cloud Messaging → iOS アプリに `.p8` を登録

## 3. Firebase / GCP プロジェクト

環境ごとに3つ作る（dev / stg / prod）。

1. Firebase プロジェクトを作成
2. **Firestore を作成するとき、ロケーションに `asia-northeast1` を選ぶ**
   （F-510。**後から変更できない**ので、ここを間違えると作り直しになる）
3. Cloud Storage も `asia-northeast1` で作成
4. Blaze プラン（従量課金）に切り替える。Cloud Functions / Cloud Tasks に必須
5. `.firebaserc` のプロジェクトIDを実際の値に合わせる

### Storage のライフサイクル（設計書 3.2）

`gcloud storage buckets update` またはコンソールで設定：

| 経過日数 | 動作 |
|---|---|
| 90日 | Nearline へ移行 |
| 365日 | Coldline へ移行 |
| 保持期間（既定13ヶ月）超 | 削除 |

### 署名付きURLのためのIAM権限

Cloud Functions が署名付きURLを発行するには、実行サービスアカウント自身に
署名権限が必要（これが無いと `capture-issueUploadUrl` が本番で失敗する）。

```bash
PROJECT_ID=worklog-prod
SA="${PROJECT_ID}@appspot.gserviceaccount.com"   # または Functions の実行SA
gcloud iam service-accounts add-iam-policy-binding "$SA" \
  --member="serviceAccount:${SA}" \
  --role="roles/iam.serviceAccountTokenCreator" \
  --project="$PROJECT_ID"
```

エミュレータでは署名できないため、`functions/src/lib/signing.ts` が
Storage エミュレータの直PUTエンドポイントを返すように分岐している。

## 4. Google Workspace SSO

### OAuth 同意画面

1. GCP Console → API とサービス → OAuth 同意画面
2. ユーザーの種類：**内部**（FREX社内パイロット）または **外部**（クライアント配布）
3. スコープは `openid` / `email` / `profile` のみ。**それ以上要求しない**
4. Firebase Authentication → Sign-in method → **Google のみ有効化**（他は無効のまま）

### OAuth クライアントID

`@react-native-google-signin/google-signin` は3種類必要になる。

| 種類 | 用途 | アプリ側の設定 |
|---|---|---|
| Web | Firebase Auth への資格情報交換 | `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` |
| iOS | iOS のネイティブサインイン | `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` |
| Android | Android のネイティブサインイン | SHA-1 の登録のみ（IDは不要） |

Android は EAS の署名鍵の SHA-1 を登録する：

```bash
cd app && pnpm exec eas credentials    # Android → Keystore → SHA-1 を確認
```

### 許可ドメインの登録（テナントの作成）

`ops-createTenant` はまだ未実装（M12）。それまでは Firestore に直接入れる。
**`/ops` 配下はクライアントから一切読めないので、Admin SDK かコンソールから操作する。**

```
/tenants/{tenantId}                          ← テナント設定（F-506 の全項目）
  allowedDomains: ["clientcorp.co.jp"]
  invites: [{ email: "admin@clientcorp.co.jp", role: "tenantAdmin" }]
/ops/registry/domainIndex/clientcorp.co.jp   ← { tenantId: "<tenantId>" }
/ops/registry/tenantsIndex/{tenantId}
```

`allowedDomains` と `domainIndex` は **両方**必要。
食い違っている場合はログインを拒否する仕様にしてある（緩い側に倒さないため）。

`invites` に入れたメールアドレスの人が初回ログインすると tenantAdmin になり、
招待は消費されて消える。`autoProvisionUsers: false` にすると、
招待または管理Webでの事前登録がない人は入れなくなる。

## 5. Cloud Scheduler / Cloud Tasks

`firebase deploy --only functions` で以下が自動作成される。

- Cloud Scheduler ジョブ（10分おきに `scheduleNotificationsJob` を起動）
- Cloud Tasks キュー `deliverCaptureNotificationQueue`

デプロイ後に確認すること：

```bash
gcloud scheduler jobs list --location=asia-northeast1 --project=<id>
gcloud tasks queues list --location=asia-northeast1 --project=<id>
```

通知が飛ばないときの切り分け順：
1. Scheduler ジョブが動いているか（Cloud Logging で `scheduleNotifications done` を探す）
2. `enqueued` が 0 でないか（0 なら休日・稼働時間外・FCMトークン未登録のいずれか）
3. Cloud Tasks にタスクが積まれているか
4. FCM の送信結果（`capture notification sent` の `failure` 件数）

## 6. 実機検証（コードでは代替できない）

受け入れ基準（要件定義書 第11章）のうち、実機でしか確認できないもの。

| # | 基準 | 確認方法 |
|---|---|---|
| 2 | 通知タップから撮影完了まで5秒以内 | 4G環境で20回測定 |

## 7. ストア審査への備え

従業員の撮影アプリなので、プライバシーの説明を丁寧に用意する。

審査で説明を求められやすい点と、実装上の答え：

| 指摘されやすい点 | 実装 |
|---|---|
| 従業員を常時監視していないか | バックグラウンド自動撮影は実装していない。通知起点の手動撮影のみ |
| 位置情報を取っていないか | 権限自体を要求していない（`blockedPermissions` で明示的にブロック） |
| 端末の写真にアクセスしないか | カメラロールの権限を要求していない (F-106) |
| 撮ったものを消せるか | 本人がいつでも削除でき、管理者でも復元できない (F-901, F-904) |
| データの保存先 | すべて東京リージョン (F-510) |

App Privacy / データセーフティの申告に必要な情報：
- 収集するもの：カメラで撮影した動画、撮影時刻、メールアドレス、氏名、所属
- 収集しないもの：位置情報、連絡先、端末内の写真・動画
- 用途：業務記録（日報・勤怠の補助エビデンス）
- 第三者提供：AI日報生成時に Claude API へ **テキストのみ**（既定）。
  画像ありモードはテナント管理者が明示的に有効化した場合のみ
